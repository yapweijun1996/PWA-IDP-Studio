# Local data model

The application stores the **2.0.0 Batch contract**. Uploads use windowed extraction: small files retain one logical document; larger files produce one document per extracted segment. Documents can contain multiple transactions. The original file is immutable, SHA-256 hashed, and stored under `file_id` in IndexedDB.

## Coverage and extraction

The complete physical page manifest is read before extraction. `maxPages` defaults to 100, clamps to 1–500 and respects stored values. Only that prefix is rendered/segmented. Remaining pages retain `pending` status and `review_pending` attribution, with a batch-level blocking `PAGE_LIMIT_EXCEEDED` issue. Raising the limit and retrying expands the stored plan. Model claims of complete processing or approval are ignored. Evidence uses unrotated top-left coordinates.

Demo requests allow only `model`, `input`, `stream`, `store`, `instructions`, `tools`, `tool_choice`, and `parallel_tool_calls`, forcing `store:false` on every agent turn. Token limits and other unlisted controls are dropped; BYOK payloads are unchanged. See [agent architecture](ARCHITECTURE-AGENT.md) for tool budgets and image forwarding.

Amounts, prices, totals and quantities are decimal strings (up to six fractional digits). Insignificant trailing zeros past the sixth digit, as in a printed price `14.90000000`, are dropped (stored as `14.90`); any longer fraction with a non-zero digit would lose precision and is reported as invalid. Reconciliation uses the shared fixed-precision decimal helpers, with their default 0.01 tolerance. A total reconciles when it equals the sum of the line amounts, or that sum plus the optional header `tax_amount` (for example 673.50 + 8% GST 53.88 = 727.38); Auto extraction also asks for `subtotal_amount` and `tax_amount` when the document prints them. Auto output is always reconciled; a Targeted template is reconciled when it declares `total_amount` as an `amount` field (the built-in *Invoice with totals* template does), reading the rows' `amount` column, and rows without an `amount` value are skipped rather than reported. A template without that field is not reconciled. Invalid decimal text is preserved for correction and reported as `INVALID_DECIMAL` (error). Required values, real ISO dates, ISO currencies and totals mismatches produce blocking issues. Confidence below 0.85 produces an evidence warning; no bounding box produces an informational issue, not fabricated evidence.

Targeted extraction retains only selected profile keys. Generic row cells are stored as ordinary values in `data.line_items`, with separate pointer-addressed evidence. Header-only profiles omit rows. Optional transaction `required_fields` (JSON pointers) and `field_types` (pointer-to-type map) preserve profile requirements and types across issue recomputation and correction; they are not business data. Amount/quantity fields normalize to decimal strings, integer fields to safe integers, and dates to ISO dates. Missing required values remain null and create blocking `MISSING_REQUIRED` issues. Auto transactions omit this metadata and retain standard document rules.

Auto statements retain one `statement` header transaction and build one `statement_entry` transaction per extracted row. Entries contain only row fields and link through the shared document, not ad-hoc references. IDs are deterministic: `t_n` for the header and `t_n_entry_<1-based row>` for entries. Per-cell evidence moves to entry-relative pointers and stays on the document pages. Present dates must be real ISO dates; amount/debit/credit/balance values normalize as decimals. An entry with neither an amount (including debit/credit) nor description gets `MISSING_REQUIRED`. Closing balance is compared with the final running balance only when closing and every running balance parse; mismatch blocks the header only.

Targeted profiles retain one transaction by default, including statements. Optional boolean `rowsAsTransactions: true` (Templates: “Each row is a transaction”) opts into header plus entry expansion; selected required fields and types move to their respective transactions. Profile import/export and batch snapshots preserve the flag.

`contract/ruleCatalog.ts` is the shared rule metadata and managed-resolution policy. UI issue titles derive from it. Catalog coverage tests inspect TypeScript emitters in contract/lib. Safe semantic exceptions (`LOW_CONFIDENCE`, `FIELD_WITHOUT_EVIDENCE`, `TOTALS_MISMATCH`) may be waived with at least ten trimmed reason characters. Pure `waiveIssue` clones the batch, increments its revision and appends an issue-targeted local-user `waive` review; `waiver_review_id` links the decision. `reopenIssue` records a `reject` review and clears the link while retaining the earlier review. Reopening uses `reject` because the frozen review action enum has no reopen action. Structural/reference/coverage, required-field, boundary and extraction failures cannot be waived. Recalculation retains matching waived issues; they no longer block eligibility. The local actor is not a production authorization boundary.

Waiver refusal coverage includes unknown issues/rules, short or whitespace-only reasons, repeated decisions, resolved issues, mandatory rule families and invalid batch coverage. Refused decisions leave the caller's batch unchanged. Successful decisions retain append-only review history and record trimmed reasons, actor/time and consecutive batch revisions. Revalidation retains an existing waiver for the same scoped target, rule and message; reopening restores its open status and export blocker where applicable.

The windowed library takes image budgets from `imageLimits(provider)` in `lib/providers.ts`, with one-page segmentation overlap:

| Provider | Request cap | Window | Extraction chunk | Tool images | Single pass |
| --- | --- | --- | --- | --- | --- |
| Demo | 4 | 4 | 2 | 2 | 2 |
| OpenAI / OpenRouter / Gemini | No app-level cap | 10 | 10 | 12 | 10 |

Demo's request cap includes replayed tool-result images; actual BYOK provider/model limits still apply. Demo 100-page processing requires approximately 34 segmentation calls plus per-document extraction calls, with extra calls for repairs/tools.

`SegmentPlan.window` stores the segmentation size; missing or different sizes invalidate cached windows and results. `SegmentPlan` and `SegmentResult[]` remain JSON-serialisable persistence sidecars. Segment page numbers and evidence remain absolute. Each extracted segment gets `d_n`, `t_n` and `r_d_n_<page>` identifiers. Unprocessed pages remain pending; failures create blocking `PAGES_FAILED`, missing decisions retain unknown attribution, and boundary confidence below 0.7 creates blocking `BOUNDARY_UNCERTAIN`. Headers come from the first chunk, and a header value that is empty there is filled from a later chunk (a value the first chunk found is never replaced); rows concatenate with adjusted evidence/required pointers. Later chunks may omit required headers; required values are checked on the merged output, not rejected per chunk. Statement expansion occurs only when building the batch after merging; persisted `SegmentResult.output` retains its header and rows, so Retry/resume rebuilds the same entry IDs for the same input.

Retry re-segments failed windows and retries failed extraction segments. Successful outputs survive only when their complete ordered page list still matches a stitched segment; changed boundaries invalidate stale results. Partial progress batches are structurally and referentially valid even before any document is extracted. `buildBatch` delegates to `buildBatchFromSegments` with the existing rendered prefix as one segment, preserving the single-document contract.


### Extraction modes and profile snapshots

Home defaults to Auto (AI decides). Targeted sends a selected profile's header fields and repeating row columns. User profiles and the selected mode are stored in `idp-studio.profiles.v1` and `idp-studio.mode.v1` in localStorage. Builtins are read-only; duplication creates an independent user profile. The built-ins are *Document info*, *Document info + rows* and *Invoice with totals* (document info, sub total, tax, grand total and rows with stock code and UOM); other code addresses the first two by position, so new built-ins are appended. In the template editor the user only names a field or column; its snake_case key is derived from the label (`keyFromLabel`), stays hidden unless *Show technical keys* is on, follows the label while the field is new, and never changes for a field that was already saved because stored data and batch snapshots refer to it. Auto mode's row keys are `stock_code`, `description`, `quantity`, `uom`, `unit_price` and `amount`. A profile's `fields` are the document-level values and its `rowFields` the row columns; there is no separate footer section, so totals such as `total_amount`, `subtotal_amount` and `tax_amount` are ordinary header fields. See [Product design](PRODUCT-DESIGN.md) for how these map to the Document Info / Row Data / Footer model and which parts are still gaps.

Templates imports and exports `{ "idp_studio_profiles": 1, "profiles": [...] }`. Parsing rejects unknown properties and invalid profile fields atomically. Import conflicts by ID or exact name require explicit rename-as-copy approval; existing profiles are never overwritten. Built-in exports import as custom profiles. Deleting the selected profile resets next-upload mode to Auto without changing batch snapshots.

The portable profile object contains `id`, `name`, `fields`, `rowFields` and optional boolean `rowsAsTransactions`; exported files omit the built-in lock flag. Fields contain `key`, `label`, `type` and optional boolean `required`. Parsing checks the versioned envelope, both field arrays, snake_case keys, cross-section key uniqueness, labels, supported types and the combined 1–30 field limit. Errors identify the profile index; any invalid entry rejects the whole file. ID-only and name-only conflicts both require approval, including collisions between entries in the same file. Approved copies receive fresh IDs and available names (`name copy`, `name copy 2`, …); cancellation changes nothing. An empty profile list is valid and imports nothing.

Before extraction, `idp-studio.batch-modes.v1` records the used mode and a deep-copied profile keyed by batch id. Retry reads this snapshot, not the current Home selection or edited/deleted profile. This sidecar leaves the strict v2 envelope and IndexedDB schema unchanged. Workspace labels use the same snapshot; full evidence JSON remains the unmodified envelope. Targeted clean JSON exports transaction data without Auto's extra `document_type` wrapper. Clear all local data removes profiles, mode and snapshots. Blocked storage retains settings and snapshots for this session only.

### Customize fields and extracting again

The review screen's **Customize fields** starts from a copy of the template the batch was read with (`loadBatchMode(id).profile`); for an Auto result it builds one with `templateFromTransaction`: the header fields and row columns that have a value, plus the fields the document type requires (`requiredKeys`, also used by `transactionView`), each typed from the types the result declares in `field_types` (a result read with a template whose saved copy is gone) or, failing that, from its key name (`fieldTypeForKey`: `*_date` date, `*quantity*` quantity, other amount-like keys amount, `*_no`/`*_code`/`currency`/`uom` code, otherwise text). Labels come from `labelFromKey`, which writes acronyms in capitals (`po_no` → "PO no"). Saved keys never change; new fields derive theirs as on the Templates page. The template is saved like any custom template.

**Save and extract again** (`reextract` in `App.tsx`) never edits the existing batch. It builds a placeholder batch with a new id (same `file_id`, same `created_at`, so the original is not copied and the list order is kept), records the template as that batch's snapshot, and runs the normal windowed extraction into it. When the run ends the new batch replaces the old one only if it is complete: status is not `failed`, it has at least one transaction, and every page is `classified`. Then `deleteBatch(oldId)` removes the old batch, its windowed state and its run history, and the app moves to the new id. If the run failed, was cancelled, or any page is not classified, the new batch is deleted and the old one is untouched. Corrections, approvals and waivers on the old batch are not carried over; the confirmation states how many there are. While the run is in progress the old batch is locked in the UI (no edits, no approval) because they would be discarded. If the tab is closed mid-run, the old batch is intact and the interrupted new batch stays beside it in Documents, where it can be retried or deleted.

A result read with a template is a Targeted result: it declares `field_types`, so type checks follow the template. The ISO 4217 currency rule applies to it too, to a field keyed `currency` (a header field or a row column): Auto mode flags any currency that is not an uppercase ISO 4217 code, empty or not, while a Targeted result flags one that is present and not a code, so an optional currency the document does not print is not an error (a required one is reported as missing). The shared system prompt already tells the model to use an ISO code in both modes.

### Sections: Document info, Row data, Footer

The review screen and the optional grouped export show a transaction in three blocks. This is applied when showing and exporting; the stored batch (schema, evidence, reviews) and the AI prompt are unchanged. A template header field may carry `section: 'info' | 'footer'` (`ProfileField` in `src/lib/agent/contract.ts`); row columns are always Row Data and may not carry it (`validateProfile` rejects both an unknown value and a section on a row column; import and export accept and keep it). `sectionOf(key, profile)` in `src/lib/sections.ts` returns the field's explicit choice, else `defaultSection(key, type)`: a key is a footer line when it contains a total or charge word (`subtotal`, `total`, `discount`, `shipping`, `freight`, `rounding`, `gst`, `vat`, `due`, or `tax` alone or ending `amount`, `total`, `fee`, `charge`), unless its last word marks an identifier, name or date (`no`, `number`, `code`, `id`, `ref`, `date`, `name`, `address`, `terms`, `method`, `type`, `mode`) or the field is a declared date, so `tax_id`, `shipping_address` and `due_date` stay in the document info. A result with no template uses the default for every key; the batch snapshot (`idp-studio.batch-modes.v1`) supplies the template's choices. The field form shows the section each field will land in, taken from its name until the user chooses; only an explicit choice is stored.

`reconcileTotals(tx)` in `src/contract/rules.ts` is the line sum against `total_amount` (plus a separately printed tax), returning null when the rule does not apply; the TOTALS_MISMATCH rule and the Footer's *Rows add up to … Matches / Does not match* check both use it, so they cannot disagree. Footer lines other than subtotal, tax and total are not part of it. `groupedJSONValue(batch, id)` in `src/lib/jsonExport.ts` returns `{ document_type?, document, rows, footer }` holding exactly the values of the clean JSON (`document_type` is present for an Auto result, as in the clean JSON); the flat clean JSON remains the contract for an ERP or API.

### Add row

`addRow(batch, transactionId, columns, values, reason)` in `src/contract/review.ts` appends one row to `data.line_items` of a transaction that has them. Rows are only ever appended, so no existing evidence pointer (`/line_items/<i>/<key>`) moves. The new row has every column the other rows have (`rowColumns` in `AddRow.tsx`: the columns of the existing rows, then the other columns of the template snapshot, else the standard Auto row keys); blank cells are `null`, text is trimmed, and values are normalized like a corrected cell (`normalizeCell`, shared with `correctField`). A column the transaction declares as `amount` or `quantity` (or, in an Auto result with no declared types, a key that `decimalKey` treats as a number) refuses text that is not a number, because `INVALID_DECIMAL` is an error and not a blocker and the totals rule skips a row whose amount is not a number, so such a value would otherwise pass approval.

In a result read with a template (`field_types` declared) the new row's cells get a declared type, taken from the same column of an existing row, else from the template column, else `text`, and the column's required mark is copied to `required_fields`, so the row is validated like the others. The row has **no evidence**: the contract (`evidence.sources` has `minItems: 1`) ties evidence to a page region and a typed row has none. Provenance is the review trail: a `correct` review on the transaction with the reason `Row added by hand: row N. <reason>`; `handEnteredRows` reads it back to show the **Entered by hand** badge, and it travels with the batch in the full evidence JSON. The clean JSON simply contains the row. Adding a row sets the transaction back from `approved`, increments the revisions, and re-runs every rule (a row that breaks the total raises `TOTALS_MISMATCH`). No schema or version change is needed.

## Review and export

`correctField` returns a new batch, increments revisions, records a local-user review and marks existing evidence as human-corrected without changing its geometry. Corrections invalidate prior approval. `recomputeIssues` resolves obsolete issues and retains resolved/waived history; recurring conditions append new issues. `approveTransaction` refuses open blockers and records explicit human approval. Batch/document statuses and advisory validation are recomputed. Workspace JSON provides clean business data or the complete batch; export and copy are disabled for ineligible transactions. Evidence boxes remain read-only.

### Human layout review

`src/contract/layout.ts` provides immutable `confirmBoundary`, `setDocumentType`, `assignPage`, `splitDocument` and `mergeDocuments`. Each operation requires a nonblank reason, rejects documents containing approved transactions, increments the batch revision and affected transaction revisions, appends a `Review` with actor `local-user`, refreshes issues/statuses and refuses invalid references or coverage. Layout reviews target a document or file-qualified page; their prior/new revisions refer to the batch envelope because documents/pages have no revision field.

- Confirmation resolves the selected document's boundary uncertainty. Type correction selects `erp.<type>` version `1.0.0`, retains statement entry types when correcting a statement, and removes old profile requirement/type metadata so the new document-type rules apply. Empty data reclassified as statement/unknown retains a required `/document_no` rather than bypassing data review.
- Assignment accepts a `{file_id, page_number}` identity (a full Page is also accepted). It classifies pending/error pages, creates a new full-page ownership region and keeps evidence unchanged. A null destination explicitly records `blank` unassigned attribution. Source/destination boundaries require review. An evidenced source page cannot leave its document. Removing a document's final page is refused because the contract requires nonempty page references; merge that document instead.
- Split accepts the first later page, not a zero-based index. A numeric page number is accepted only when unambiguous across files. Later page regions move without geometry changes. Evidence wholly on the later side moves with its transaction; mixed transactions get a new transaction identity for their later evidence, preserving data and pointer resolution and leaving retained evidence on the original transaction. Evidence whose sources straddle both sides is refused rather than truncating provenance. A separate empty transaction always requires data review. It inherits nonempty profile requirements/types, otherwise standard type requirements; statement/unknown empty transactions without requirements require `/document_no` so confirming a boundary cannot silently make empty data exportable. Required top-level pointers are visible in the transaction view and remain editable in Workspace even when a profile snapshot exists.
  Statement entries with evidence on both sides cannot be split across documents; whole entries move only when their evidence stays on the destination document's pages. Entries without evidence remain with their current document.
- Merge keeps the first selected document's type/schema and all transaction identities/types, reparents transactions/evidence/regions, orders page references by the physical manifest and requires boundary review. Document issues are retargeted before recomputation so no orphan references remain; audit history is retained.

Label Studio persists completed envelopes with `putBatch` and refreshes the shared batch list. After saving, it pins the current batch selection so resolving its final layout issue cannot switch the reviewer to another batch. It never edits source files or evidence geometry. Export eligibility remains transaction-scoped: split data must be completed and its boundary confirmed before export.

## Storage and legacy data

IndexedDB version 4 retains `documents`, `files` and `batches` (`{ batch, createdAt }`, keyed by nested batch id), plus the v3 `windowed` store, keyed by batch id with `{ plan: SegmentPlan, results: SegmentResult[] }`, and adds `runs` (below). Progress atomically commits both batch and sidecar for crash/refresh recovery. Outputs never enter localStorage. Cancel stores a `review_required` partial batch; Retry reuses successful segments. Both batch deletion paths and storage clearing remove sidecars. UI deletion also removes unshared originals and matching legacy migration sources; low-level `deleteBatch` retains originals.

Startup migration is idempotent by `legacy_<id>`. It hashes original bytes, reads PDF/image dimensions and writes a new batch and file-id-keyed blob. Missing originals are skipped. If dimensions cannot be read, 595×842 fallback dimensions are disclosed in an info issue; page count uses PDF metadata when available, otherwise the saved count. Pages beyond the saved rendered-page count remain pending. Legacy `receipt`/`other` become `unknown` with `LEGACY_TYPE_UNMAPPED` warnings. Field-edit audit entries become reviews. Explicit legacy human approval is retained with a `legacy_user` approval review, but current blockers still prevent export.

New uploads accept PDF, PNG, JPEG and WebP. The v2 media enum also retains TIFF for existing records, but new TIFF uploads are refused. Image manifests and rendering decode the original bitmap with `createImageBitmap`; model images remain JPEG. Unsupported legacy media are preserved and counted as skipped, never relabeled as another format. Settings > Data displays migration counts for the current startup.

## JSON Explorer

Explorer selects from all loaded stored batches without filtering by approval. It is an inspection surface, not an approval operation: full JSON download/copy deliberately includes unapproved data, while the panel separately reports recomputed export-eligible transaction ids (none when structural/reference validation fails). Workspace retains its existing eligibility gates.

`src/lib/jsonExport.ts` owns serialization and the transaction export shape shared with Workspace: native stable insertion order with two-space indentation; Auto includes `document_type`, targeted profiles export only transaction data using the saved batch-mode snapshot. Full JSON preserves the complete v2.0.0 envelope and advisory `validation` object unchanged. The validation panel uses fresh validator codes/messages, not those advisory flags. Byte size is UTF-8 serialized full JSON; node count includes root, containers and scalar values. Transaction field pointers backed by evidence link to `workspaceHref` for that transaction; geometry remains read-only.

Clipboard refusal does not change the selected export or stored batch: Explorer exposes the same serialized text for manual copying and reports failure rather than claiming a successful copy. Clipboard permission waits are bounded; downloads remain independent of clipboard availability.

Explorer mounts only the active scope and initially opens its top-level containers, leaving deeper data lazy and collections capped at 100 visible children until expanded further. If a batch has no transactions, Transaction shows “No transactions”, mounts no tree and disables Download full JSON; Full batch still exposes the complete envelope for inspection and download. Transaction selection resolves against the current batch so removal of the selected transaction cannot attempt an unknown export.

### Run traces (IndexedDB v4)

The additive `runs` store is keyed by run `id`. Each row stores batch id, filename, provider/model, mode/profile name, started/ended epoch timestamps, segmentation-window and extracted/failed-document counts, outcome (`validated`, `review_required`, `failed`, `cancelled`), bounded steps `{at, tool, summary, ok}` and safe error text. Writes project allowed fields, replace tool summaries with payload-free status text, cap steps at 200, and atomically prune to the newest 50 runs. Both batch deletion paths remove matching runs; clear-all clears the store and `idp-studio.agent-config.v1`. The v3-to-v4 migration retains originals, batches and recovery sidecars.
